01

How git actually works

Almost every confusing git message makes sense once you know this: your code exists in four separate places, and git commands are just moves between them. Most people learn the commands without the map, which is why the errors feel random.

01
Working tree
Your actual files on disk. What you edit in VSCode.
02
Staging area
A shortlist of changes you've marked for the next commit.
03
Local repository
Your commit history, saved in the hidden .git folder.
04
GitHub
The shared copy both machines talk to. Called origin.
git addtree → staging
git commitstaging → local
git pushlocal → GitHub

And git pull runs the whole chain backwards: it brings commits down from GitHub and updates your files.

Why the staging area exists

It lets you commit some of your changes and not others. If you fixed a boundary condition and also left some debug printing in a solver, you can stage and commit just the fix. Everything not staged simply stays as it is, uncommitted, waiting for you.

Reading git status

This is the single most useful command in git. Run it constantly — before staging, before committing, before pulling, whenever you are unsure. It tells you where you are and what state everything is in.

Terminal

$ git status

On branch main
Your branch is up to date with 'origin/main'.          # in step with GitHub

Changes to be committed:                                # STAGED — will be in next commit
        modified:   src/.../meanWaveLoads.C

Changes not staged for commit:                          # edited but NOT staged
        modified:   applications/solvers/shipFlow/shipFlow.C

Untracked files:                                        # brand new, git ignores until added
        src/.../newBoundaryCondition/

Three groups, three meanings. Staged goes into your next commit. Not staged means git knows the file but you haven't marked the change. Untracked means git has never seen this file and will keep ignoring it until you git add it — this is why new files are so easy to lose.

02

The daily loop

This is the whole workflow. Five commands, in this order, every working session. If you do nothing else in this guide, do this.

A complete session

# 1. START — always pull first, before touching anything
$ cd ~/OpenFOAM/nikospe-v2412
$ git pull

# 2. WORK — edit code, compile, run cases
$ ./Allmake.sh --no-clean

# 3. REVIEW — see exactly what you changed
$ git status
$ git diff                       # line-by-line, q to quit

# 4. STAGE + COMMIT — describe what you did
$ git add -A
$ git commit -m "Add 2nd-order damping term to wave BC"

# 5. FINISH — send it to GitHub
$ git push

Staging: choosing what goes in

CommandWhat it stagesWhen to use it
git add -A Everything changed, new, and deleted The usual choice. Safe once .gitignore is set up.
git add path/to/file.C One specific file When you want to commit one fix separately.
git add src/ Everything under a folder Committing one library's worth of work.
git restore --staged f.C Un-stages it (keeps your edits) You staged something by mistake.

Writing commit messages

Future-you reads these while trying to find when a result changed. Say what changed and why, not "update" or "stuff". A good message finishes the sentence "this commit will…".

Good

Fix mean wave loads by including y-density term
Add forward-speed effect to line integral in meanWaveLoads
Reduce roll damping from 5% to 2% of critical

Useless six months later

update  ·  stashing  ·  fix  ·  asdf  ·  new code

Committing often is free

A commit is a save point, not a publication. Commit whenever something works, even partially. Small frequent commits make it far easier to find where a bug crept in — and cost you nothing. You can push several commits at once.

03

Working on two machines

GitHub is the meeting point. Neither machine talks to the other directly — both talk to origin. Think of it as the single source of truth that both copies sync against.

Laptop

~/OpenFOAM/nikospe-v2412

Finish a session by pushing, so the work is on GitHub before you walk away.

$ git add -A
$ git commit -m "..."
$ git push

Remote workstation

where you run the big cases

Start a session by pulling, so you begin from the latest work.

$ git pull
$ ./Allmake.sh
# ... run cases ...

The four rules

1

Pull before you start. Push before you stop.

Make it muscle memory. Nearly every painful git situation traces back to a skipped pull or an un-pushed commit sitting on the wrong machine.

2

Never copy the project folder between machines.

Use git push and git pull only. Copying with scp, rsync or a file manager also copies the hidden .git folder, which silently replaces the entire history on the receiving machine — commits and all.

3

Don't leave work uncommitted overnight.

Uncommitted changes exist on exactly one machine and in no history. They are the easiest thing in the world to lose. Commit, then push.

4

Work on one machine at a time.

Editing the same files on both machines before pushing creates a divergence you then have to merge by hand. Finish, push, switch.

The mistake that cost the most

Copying the whole project folder from the workstation onto the laptop overwrote the laptop's .git directory. A completed merge commit vanished — not corrupted, it simply no longer existed in that history. The code survived only because it happened to still be sitting in the working tree, uncommitted. Copy files, or use git. Never both.

If both machines have changes

Sooner or later you'll commit on both sides before pushing. Git will refuse the push and say the remote "contains work that you do not have locally". This is git protecting you, not breaking. Fix it by pulling first, which merges the two histories: 

$ git pull                       # merges GitHub's work into yours
# resolve any conflicts (see section 06), then:
$ git push
04

Setting up credentials

GitHub stopped accepting account passwords over HTTPS years ago. You authenticate with either a Personal Access Token or an SSH key. On a shared or multi-user remote workstation, prefer SSH — a token saved with the store helper is written to disk in plain text.

Option A — SSH key (recommended for the workstation)

On the remote workstation

# 1. Create a key (press Enter at each prompt; add a passphrase if you like)
$ ssh-keygen -t ed25519 -C "nikos.petik@gmail.com"

# 2. Show the PUBLIC key — copy the whole line
$ cat ~/.ssh/id_ed25519.pub
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA... nikos.petik@gmail.com

# 3. On github.com: Settings → SSH and GPG keys → New SSH key
#    Paste it, give it a name like "workstation", save.

# 4. Test
$ ssh -T git@github.com
Hi petik13! You've successfully authenticated...

# 5. Point the repo at the SSH address instead of HTTPS
$ cd <your repo>
$ git remote set-url origin git@github.com:petik13/nikospe-v2412.git
$ git remote -v                  # confirm it now says git@github.com

Public vs private key

Only ever share the .pub file. The matching file without the extension is your private key — it never leaves the machine and never goes on GitHub.

Option B — Personal Access Token over HTTPS

# 1. On github.com: Settings → Developer settings →
#    Personal access tokens → Tokens (classic) → Generate new token
#    Scope: check "repo". Copy the token — shown only once.

# 2. Tell git to remember it after the first use
$ git config --global credential.helper store

# 3. Push once; paste the TOKEN when asked for the password
$ git push
Username: petik13
Password: <paste the token, not your GitHub password>

Where the token ends up

credential.helper store writes it unencrypted to ~/.git-credentials. That is acceptable on a machine only you use. Never commit that file, and never run git init in your home directory — a repo there would put your token, shell history and SSH config one git add -A away from being published.

Set your identity on each machine

Commits are labelled with this. Do it once per machine.

$ git config --global user.name  "petik13"
$ git config --global user.email "nikos.petik@gmail.com"

Getting the repository onto a new machine

Clone it — never copy it.

$ git clone git@github.com:petik13/nikospe-v2412.git
$ cd nikospe-v2412
$ ./Allmake.sh                   # compile: binaries are not in git

Starting fresh on a machine that already has a copy

When a machine's copy has drifted far enough that untangling it isn't worth the effort, the cleanest move is to delete it and clone again. GitHub holds the truth; the local copy is disposable. But check for work that exists only on that machine first — once the folder is gone, anything never pushed is gone with it.

Step 1 — Check before you delete

Run all four. If every one comes back empty, nothing is at risk.

$ cd <the old copy>
$ git status --short             # uncommitted edits + untracked files
$ git stash list                 # forgotten stashes
$ git fetch origin
$ git log --branches --not --remotes --oneline
#   ^ THE IMPORTANT ONE: commits on any local branch
#     that exist nowhere on GitHub

If that last command prints anything

Those commits exist only on that machine. Push them before deleting anything: git push origin <branch> — or, if you don't want them on main, park them on a branch of their own: git push origin HEAD:rescue-workstation. You can sort out what to keep later, from any machine.

Step 2 — Save anything that isn't code

Case directories, meshes and results are usually not in git — they're often ignored or were never added. Copy anything you still need somewhere outside the folder before it goes. 

$ cp -r run/myImportantCase ~/keep/    # results are not in git

Step 3 — Delete and re-clone

$ cd ~/OpenFOAM
$ mv nikospe-v2412 nikospe-v2412.old   # rename, don't rm — reversible

$ git clone git@github.com:petik13/nikospe-v2412.git
$ cd nikospe-v2412
$ git log --oneline -3                 # confirm it matches GitHub
$ ./Allmake.sh                         # compile from scratch

# Only once the new copy builds and runs:
$ rm -rf ~/OpenFOAM/nikospe-v2412.old

Rename first, delete last

mv costs nothing and buys you a full undo. Keep the old folder until the fresh clone has compiled and produced results you trust — then remove it. Deleting first and discovering the problem afterwards is the one order with no way back.

05

What never to commit

Git is for source. Everything OpenFOAM's wmake generates must stay out of it. Compiled files are large, change on every build, and — critically — git cannot merge them. Two machines that both compiled the same library produce two different binaries, and every merge becomes a conflict git cannot resolve.

What this cost, concretely

One merge of this repository produced 44 conflicts. Only 4 were real source conflicts. The other 40 were .o files, .so libraries and lnInclude symlinks — pure noise that buried the four that actually mattered.

The .gitignore now in the repository

.gitignore

# Compiled binaries and libraries (wmake output tree)
platforms/

# Per-target build directories. The leading **/ is required —
# a pattern with a slash is otherwise anchored to the repo root.
**/Make/linux*/

# Auto-generated symlink farms
lnInclude/

# Objects, libraries, dependency files
*.o
*.so
*.a
*.dep

# Logs and editor noise
log
*.log
*~
*.swp

Keep these — they are source

Make/files and Make/options are hand-written and belong in git. Only the generated Make/linux64GccDPInt32Opt/ directory beside them is ignored.

Always rebuild after pulling

Because binaries aren't in git, a fresh clone or a pull that changes source leaves you without up-to-date libraries. Compile before running anything: 

$ ./Allmake.sh                   # full rebuild (wclean + wmake)
$ ./Allmake.sh --no-clean        # incremental, much faster

If you already committed build files

--cached removes them from git while leaving them on your disk: 

$ git rm -r --cached platforms/
$ git commit -m "Stop tracking build artifacts"

Expect deletions on the other machine

When the other machine pulls this, git deletes those files there — they are no longer tracked. That is intended, but it means the compiled solvers disappear until you run ./Allmake.sh again.

06

When things go wrong

Git error messages are blunt but honest. Here are the ones you'll actually meet, what each means, and the fix.

Merge conflicts

A conflict means both sides changed the same lines and git won't guess. It marks the spot and hands it to you: 

    scalar epsilon = 0.0;
<<<<<<< HEAD                    # your version
    const scalar damping = 0.05;
=======
    const scalar damping = 0.02;    # the incoming version
>>>>>>> origin/main

To resolve: open the file, delete the three marker lines, and leave the code you want — which may be one side, the other, or a combination. Then:

$ git add path/to/resolved/file.C
$ git commit                     # finishes the merge

Search before you commit

Committed conflict markers are a real hazard — this repository had a file with <<<<<<< baked into a commit. Check first: git grep -n "<<<<<<<" should print nothing.

Common errors, decoded

MessageMeaning & fix
needs merge
you need to resolve your current index first		 An unfinished merge is blocking you. Finish it, or abandon it with git merge --abort.
Updates were rejected because the remote contains work that you do not have The other machine pushed first. Run git pull, resolve anything that conflicts, then git push.
could not read Username for 'https://github.com' No credentials configured. See section 04.
Your branch is ahead of 'origin/main' by N commits Not an error. You have N commits not yet on GitHub — git push.
Your local changes would be overwritten by merge Uncommitted edits clash with what's coming in. Commit them, or stash with git stash, pull, then git stash pop.
detached HEAD You're viewing an old commit, not a branch. Get back with git switch main.

Undoing things

You want to…Command
Discard edits to one file (unrecoverable)git restore file.C
Un-stage a file, keeping the editsgit restore --staged file.C
Change the last commit's messagegit commit --amend
Undo the last commit, keep the changesgit reset --soft HEAD~1
Abandon an in-progress mergegit merge --abort
Undo a commit that's already pushedgit revert <hash>
Set work aside brieflygit stash … git stash pop

Handle with care

git reset --hard and git restore permanently destroy uncommitted work — there is no undo, because git never had a copy. Always run git status first to see exactly what you're about to lose. Prefer git revert for anything already pushed: it undoes a change by adding a new commit, rather than rewriting history other machines have already seen.

The safety net: reflog

If you commit something and then lose it — a bad reset, a branch deleted too eagerly — git remembers where you've been for about 90 days. reflog is the closest thing to an undo history: 

$ git reflog                     # every position HEAD has been in
d56e7c5 HEAD@{0}: commit: Allmake.sh: build every user library
14a6caf HEAD@{1}: merge diffOnly: Merge made by the 'recursive' strategy
888b3b3 HEAD@{2}: checkout: moving from diffOnly to main

$ git reset --hard 14a6caf       # go back to that exact state

The limit worth knowing

Reflog only covers commits this machine made. It cannot recover work that was never committed, and it cannot recover a history that was overwritten by copying a .git folder from elsewhere — which is exactly why rule 2 in section 03 matters.
